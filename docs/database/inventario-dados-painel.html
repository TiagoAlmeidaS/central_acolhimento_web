Esta sessão não tem credencial de acesso, então o que está aqui é a estrutura: quais colunas existem, o que cada KPI lê e o que é impossível responder com o modelo atual. 01

O que dá para medir hoje

Cada pergunta que o painel deveria responder, a coluna de onde a resposta sairia, e o veredito.

Quantas pessoas entraram no período? seeds.created_at — timestamp confiável, preenchido por default em toda linha. Mede
Em que etapa cada pessoa está? seeds.status (6 valores) e members.status (4 valores). Duas escalas paralelas para a mesma jornada — somar as duas exige uma regra de tradução que hoje só existe na UI. Mede
Quem está sem cuidador? seeds.caregiver_id e members.caregiver_id, ambos nulos quando não há vínculo. Mede
Quanto tempo até o primeiro contato? first_contact_at − created_at. Só para quem tem o campo preenchido; a cobertura é desconhecida até rodar a consulta 3. Mede
Quantas pessoas reuniram, com que frequência? church_attendance_records.status sobre ocorrências com attendance_closed_at preenchido. É a parte mais bem modelada do sistema: base elegível explícita e falta justificada separada da falta. Mede
Qual a carga de cada cuidador? Contagem de members e seeds por caregiver_id, mais o último followups.occurred_at. Mede
Onde a pessoa está? city, state, latitude, longitude — todos opcionais na prática. O texto é NOT NULL DEFAULT '', as coordenadas são nulas quando ninguém usou o seletor de mapa. Parcial
De onde a pessoa veio? seeds.outing_event_id é confiável e responde por saídas. seeds.source é texto livre sem taxonomia: agrupar por ele devolve a lista do que cada pessoa digitou. Parcial
Quem mudou o status, e quando? seed_status_history com changed_by_tenant_user_id — mas só desde a migração de 30/08/2026, e só para mudanças de status. Parcial
Quem cadastrou a pessoa? Nenhuma coluna guarda isso. created_by_tenant_user_id existe em 7 tabelas — saídas, tipos de saída, tipos de reunião, vínculos de igreja, sessões de TCI, convites e canais de cadastro — e não existe em seeds, members nem followups. Não mede
Por qual canal público a pessoa chegou? caregiver_signup_channels tem token, limite de uso e aprovação — mas só cadastra cuidador. Não existe canal equivalente para pessoas. Não mede
Quantas ações estão de fato em aberto? followups.next_action_at nunca recebe baixa — não há coluna de conclusão. Uma ação cumprida continua vencida para sempre. Não mede

03

Onde a medição sai errada hoje

Seis pontos em que o painel mostra um número que não significa o que o rótulo promete.

01

"Contatos Vencidos" conta linhas, não pessoas — e só cresce

O KPI conta todo followup cujo next_action_at já passou. Como nada marca uma próxima ação como cumprida, a ação de março continua vencida em setembro, e quem foi acompanhado dez vezes entra dez vezes na conta. O número não mede pendência: mede idade do histórico.

coord/page.tsx:737 · followups.filter(f => f.nextActionAt && new Date(f.nextActionAt) < new Date())
02

Os KPIs de fila ignoram o período selecionado

Triagem, esperando visita, sem cuidador e urgentes são contados sobre a lista inteira carregada em memória, sem recorte de data. A aba tem seletor de período do lado, e ele não afeta nenhum deles — dois números na mesma tela respondem a recortes de tempo diferentes sem avisar.

dashboard-status-utils.ts:5 · countOperationalAlerts(members, seeds)
03

Dois fusos horários na mesma página

O bloco de Pessoas fixa America/Sao_Paulo e calcula os limites do período em UTC-3 explícito. O resto do painel — gráfico de 7 dias, contatos da semana, ações vencidas — usa new Date() no fuso do servidor. Perto da virada do dia, as duas metades da tela discordam sobre que dia é hoje.

people-dashboard.ts:19 · PEOPLE_DASHBOARD_TIMEZONE = "America/Sao_Paulo"
04

"Vazio" e "não informado" são a mesma coisa

source, city, state, phone, address e notes são NOT NULL DEFAULT ''. String vazia é um valor legítimo, então o banco não distingue o campo que ninguém preencheu do campo que alguém decidiu deixar em branco. Nenhuma métrica de completude é confiável sem tratar '' como ausência — é o que a consulta 3 faz.

create_mvp_monolith_schema.sql:76 · source TEXT NOT NULL DEFAULT ''
05

A origem some quando o contato vira membro

members não tem coluna de origem. A única ponte é members.seed_id, que é nullable: membro cadastrado direto, sem passar por contato, não tem de onde veio e nunca terá. Qualquer análise de origem sobre a base consolidada precisa desse join e vai perder essas pessoas.

members.seed_id UUID REFERENCES seeds(id) ON DELETE SET NULL
06

A criação não é auditada, nem retroativamente

seed_status_history só recebe linha quando o status muda — a inserção do contato não gera evento. Não existe nenhuma linha com previous_status is null, então não dá para reconstruir quem cadastrou nem olhando para trás. A consulta 4 confirma isso em um número.

mvp-repository.ts:1034 · if (currentSeed.status !== nextStatus) { insert into seed_status_history … }
04

Kit de medição

Oito consultas prontas para rodar contra a base e transformar esta estrutura em números. Todas varrem todos os tenants — acrescente where tenant_id = '…' para recortar por localidade.

1 · Cobertura de origem

Quantos contatos têm alguma origem registrada, e quantos não têm nenhuma.

select
  count(*)                                            as contatos,
  count(*) filter (where btrim(source) <> '')         as com_source_livre,
  count(*) filter (where outing_event_id is not null) as de_saida,
  count(*) filter (where btrim(source) = ''
                    and outing_event_id is null)     as sem_origem,
  round(100.0 * count(*) filter (where btrim(source) = ''
                    and outing_event_id is null)
        / nullif(count(*), 0), 1)                     as pct_sem_origem
from seeds;

2 · A taxonomia que já existe de fato

O que as pessoas digitaram em source — a lista real, antes de fechar qualquer enum.

select
  coalesce(nullif(btrim(source), ''), '(vazio)') as origem,
  count(*)                                       as pessoas
from seeds
group by 1
order by pessoas desc, origem;

3 · Preenchimento dos campos que o painel exibe

Tratando string vazia como ausência — é isso que a armadilha 04 exige.

select
  count(*)                                                  as contatos,
  count(*) filter (where btrim(phone) <> '')          as com_telefone,
  count(*) filter (where btrim(city)  <> '')          as com_cidade,
  count(*) filter (where btrim(state) <> '')          as com_estado,
  count(*) filter (where latitude is not null)         as com_coordenada,
  count(*) filter (where age is not null)              as com_idade,
  count(*) filter (where caregiver_id is not null)     as com_cuidador,
  count(*) filter (where first_contact_at is not null) as com_1o_contato
from seeds;

4 · A prova do buraco de autoria

eventos_de_criacao deve voltar zero. É a confirmação de que quem cadastrou não é recuperável.

select
  (select count(*) from seeds)                     as contatos,
  (select count(*) from seed_status_history)       as eventos_de_status,
  (select count(*) from seed_status_history
     where previous_status is null)                as eventos_de_criacao,
  (select count(*) from seed_status_history
     where changed_by_tenant_user_id is null)      as eventos_sem_autor;

5 · Funil real por status

A distribuição da base, sem depender da tradução que a UI faz entre as duas escalas.

select 'contato' as tipo, status::text, count(*) as pessoas
from seeds group by 1, 2
union all
select 'membro', status::text, count(*)
from members group by 1, 2
order by tipo, pessoas desc;

6 · Tempo até o primeiro contato

Média e mediana em dias, sobre quem tem first_contact_at.

select
  count(*)                                                    as abordados,
  round(avg(extract(epoch from (first_contact_at - created_at))
            / 86400)::numeric, 1)                             as media_dias,
  round((percentile_cont(0.5) within group (
     order by extract(epoch from (first_contact_at - created_at))
              / 86400))::numeric, 1)                          as mediana_dias
from seeds
where first_contact_at is not null
  and first_contact_at >= created_at;

7 · Frequência da igreja sobre base fechada

Só chamadas com attendance_closed_at entram — é a mesma regra que o painel aplica.

select
  count(distinct o.id) filter (
    where o.attendance_closed_at is not null)        as chamadas_fechadas,
  count(distinct o.id) filter (
    where o.attendance_closed_at is null
      and o.status <> 'cancelled')                  as chamadas_pendentes,
  count(a.id) filter (where a.status = 'present')   as presencas,
  count(a.id) filter (where a.status = 'absent')    as faltas,
  count(a.id) filter (where a.status = 'justified') as justificadas,
  count(a.id) filter (where a.status = 'unmarked')  as nao_marcadas
from church_meeting_occurrences o
left join church_attendance_records a
       on a.occurrence_id = o.id
      and o.attendance_closed_at is not null
where o.occurs_on >= current_date - interval '90 days';

8 · Ações vencidas: linhas contra pessoas

A diferença entre as duas colunas é exatamente o tamanho da armadilha 01.

select
  count(*)                    as linhas_vencidas,
  count(distinct member_id) as pessoas_envolvidas,
  min(next_action_at)::date   as mais_antiga
from followups
where next_action_at is not null
  and next_action_at < now();
